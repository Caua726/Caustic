# v0.1.2 — one binary, two architectures, three systems

CSE stops being an x86_64 format. A single `.cse` now carries native code for
x86_64 **and** AArch64, and the polyglot form carries every body Windows, Linux
and CausticOS need — six in one file.

## The container

`--target=caustic` (or the explicit `caustic-x86_64-aarch64`) builds one image
per architecture and fuses them:

```sh
caustic --target=caustic prog.cst -o prog.cse
```

```
CST_ 3.1  2 images
  arch=1 x86_64   -> slice CST_ 3.0
  arch=2 aarch64  -> slice CST_ 3.0
```

The container is a thin index over complete, unmodified images: each slice is
byte-identical to what a single-target link emits, so the loader picks an entry
and parses from there exactly as before. `caustic-x86_64` and `caustic-aarch64`
each name one architecture, the way `linux-x86_64` and `windows-x86_64` always
have. A single-architecture link produces the same container holding one slice,
so every `.cse` has one shape.

The version is major.minor in two bytes rather than one u16 — a container is
3.1, the images inside it 3.0.

## The polyglot

`--mode=compat` welds six bodies into one file:

```
offset     0  MZ    PE       Machine=0x8664   -> Windows x86_64
offset  4096  ELF   x86-64                    -> Linux x86_64
offset 12944  ELF   AArch64                   -> Linux ARM64
offset 21792  MZ    PE       Machine=0xaa64   -> Windows ARM64  (carried, see below)
offset 25408  CST_  slice    arch=1           -> CausticOS x86_64
offset 25552  CST_  slice    arch=2           -> CausticOS ARM64
```

A shell stub picks the Linux body from `uname -m`; CausticOS finds its container
through the `CST*` mini-header; Windows loads the PE at offset 0.

The ARM64 Windows body is present and locatable but not yet reachable: the PE
loader reads a single COFF Machine, so an ARM64 host running this file gets the
x64 body under emulation. Activating the native one means the entry stub
detecting the machine via `IsWow64Process2` and relaunching — that stub is not
written.

## AArch64 gains

- **Windows FFI.** `IR_FFI_CALL` was rejected outright on this backend. Windows
  on ARM64 follows AAPCS64 — the convention the backend already emits — so there
  is no argument reshuffle and no shadow space; the call reaches the IAT through
  `adrp`/`add`/`ldr` with x16.
- **`--target=windows-aarch64`** produces a PE stamped ARM64, with an AArch64
  entry stub, an AArch64 `CommandLineToArgvA` equivalent, and 8-byte `.pdata`
  entries carrying packed unwind words. Not yet runnable end to end — see below.
- **`--target=caustic-aarch64`** for CausticOS on ARM.

## COFF object writer

`caustic-as` on a Windows target printed "not yet implemented" and exited. It
now emits real `.obj` files — header, section table, per-section relocations,
symbol table, string table — for both AMD64 and ARM64. Verified round-trip:
`caustic-as` → `.obj` → `caustic-ld` → PE → runs.

## `with section(...)` on functions

Documented since the beginning, silently ignored in practice: only globals ever
got a `.section` directive, so a function carrying the annotation went to
`.text` with no diagnostic. It now works end to end — the flag survives into the
object as `SHF_EXECINSTR`, the linker places such a section inside the
executable segment, and a `.cse` maps it R+X.

## Fixes

- **`.csl` did not load.** The CSL header grew from 32 to 44 bytes when v2 added
  the kernel32 import fields and the loader was never updated, so `csl_open`
  failed for every shared library the current writer produces.
- **A polyglot could be broken by its own size.** The `CST*` mini-header stored
  offsets as raw u64 inside the shell-quoted region; a body offset anywhere in
  `[0x2700,0x27FF]` — and every 64 KiB window after — put a `0x27` there, closed
  the quote early and made `/bin/sh` execute the embedded machine code. Both
  fields are ASCII decimal now, and the link fails if a quote byte ever appears
  in that region.
- **CodeView debug directory in a polyglot** pointed 512 bytes short: the APE
  combiner shifted the PE without patching `IMAGE_DEBUG_DIRECTORY`'s file offset.
- **Segment ceiling.** The writer allowed 39 segments where the loader accepts
  16, so a program with enough custom sections built clean and failed at load.
- **Silent truncation** replaced with errors: imports past the 1024-entry table,
  sections past the segment limit.
- **`opt_cse`** now carries `cast_to` in its key. Codegen reads it to pick `sar`
  vs `shr` and to truncate narrow results, so two instructions with identical
  operands and different `cast_to` are not the same value. Nothing in the IR
  guaranteed they could not meet.
- **`csl_loader`** validates the version and architecture, bounds every offset
  against the file, loops its read, and keeps one slot per open image so a
  second `csl_open` no longer replaces the first.

## Known limits

- **Windows ARM64 is emulated, not native.** The body is in the file; the
  re-exec stub that would reach it is not written.
- **AArch64 unwind is minimal.** Every function is described as saving nothing
  and chaining nothing — correct for execution and symbol lookup, but a stack
  walk will not recover callee-saved registers.
- **The Linux path in a polyglot is not kernel-level.** With `MZ` at offset 0,
  `execve` returns `ENOEXEC` and the file runs because a shell re-reads it as a
  script. Callers that are not shells — `make`, `systemd`, `subprocess` without
  `shell=True` — cannot launch it, and a `binfmt_misc` entry claiming `MZ` will
  intercept. Registering the format with `binfmt_misc` fixes this without
  changing the binary.
