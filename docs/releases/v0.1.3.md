# v0.1.3 — the shared stdlib on Windows, and installers you can steer

v0.1.2 shipped the multi-architecture CSE. This one makes the Windows side of
the stdlib real, turns the installers into something you configure rather than
accept, and closes the gaps in the gate that let the last round's bugs through.

## libcaustic.dll

The Windows shared stdlib could not be produced at all. A `--shared` build keeps
every symbol — that is what a library is — so `std/os/linux.cst`'s wrappers are
emitted whether or not the target has syscalls, and each one carries a raw
`syscall` the Windows backend refuses.

`--allow-unsupported` already means "emit this target even though some paths
cannot work here"; it downgrades `__compile_error` on exactly that basis. The
syscall gate now honours it too, returning `-ENOSYS` instead of aborting.

Verified under wine rather than merely built: a Windows program importing the
DLL calls through it, including `_std_io_cst_write_str`, which reaches the
console via the DLL's own kernel32 imports. 784 exports; a real import table for
kernel32, ntdll, bcrypt and ws2_32.

The export directory also names the file it belongs to now — it was a fixed
`caustic.dll` whatever the library was actually called.

## Installers

Three decisions, the same on both systems, each with a flag and an interactive
prompt:

| | Linux | Windows |
|---|---|---|
| where | `--user` · `--system` · `--prefix=` · `--root=pkexec\|sudo\|doas` | `-Prefix` · `-System` (elevates through UAC) |
| compiler | `--format=elf,cse,exe` | `-Format exe,cse` |
| tools | `--tools=as,ld,mk,lsp` | `-Tools ...` |
| shared stdlib | `--lib=so,csl,dll` | `-Lib dll,csl` |

`cse` installs the universal build: one file with a native body for Linux,
Windows and CausticOS on x86_64 and ARM64. The first format listed owns the
plain `caustic` name. `--dry-run` prints the plan and touches neither the disk
nor the network.

**update** and **uninstall** exist now, on both systems. The installer records
what it chose and every path it wrote, so `update` replays your configuration
instead of reverting to the defaults, and `uninstall` removes what it created
and nothing else — a shared prefix like `/usr/local` keeps everything that is
not Caustic.

```sh
./update.sh --check      # installed vs latest, changes nothing
./uninstall.sh --dry-run # what would go
```

## --extension does something

It was parsed, validated, stored — and never read; the output name came from
`-o` alone. It now names the suffix a CSE output carries, which is always
`.cse`, plus `.<ext>` unless `<ext>` is `cse` itself. Never a bare `.exe`.
The default is `exe`, because the polyglot's offset 0 is an MZ header and
Windows will not run the file without it.

```
-o prog                  ->  prog.cse.exe
-o prog.exe              ->  prog.cse.exe
--extension=cse -o prog  ->  prog.cse
--extension=com -o prog  ->  prog.cse.com
```

## The gate

Two bugs shipped in v0.1.2 through a green pre-commit, and both had the same
shape: nothing in the gate ever built the target that broke.

- `std/os/causticos.cst` emitted a bare `mfence`, so it could not be assembled
  for AArch64 at all.
- ARM64 COFF relocations were translated through the AMD64 table, linking a
  `windows-aarch64` PE with unrelocated call sites.

Compiling for another architecture needs no external tool — only *running* the
result does, which is why `check-cross.sh` stays opt-in. So the gate now builds
all seven targets and all three `libcaustic` flavours, and fails if a link
leaves a relocation unapplied. It also loads a `.csl` through `csl_loader` and
checks the container carries a slice per architecture: the `.csl` was broken for
an entire release because nothing exercised it.

`release-build.sh` builds all three release assets and refuses one that does not
run; `prerelease.sh` warns when an asset the previous release shipped is
missing. v0.1.2 went out with one download where v0.1.1 had two, and nothing
noticed.

## Fixes

- `mfence` is gated per architecture; AArch64 gets `dmb ish`.
- ARM64 COFF relocations map through the ARM64 table in both directions, and
  `CONDBR19` no longer falls through to `ADDR64`.
- The COFF reader allocates the custom-section exec bits, which it did not —
  `merge_sections` dereferenced null for every COFF input.
- The ARM64 sub-build's `.pdb` is cleaned up; only the x64 one was.

## Known limits

Unchanged from v0.1.2: Windows on ARM64 runs the x64 body under emulation (the
native body is carried, the re-exec stub that reaches it is not written);
AArch64 unwind describes every function as saving nothing; and a polyglot's
Linux path runs the native ELF but not through `execve`.
