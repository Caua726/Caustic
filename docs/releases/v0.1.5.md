# v0.1.5 — 2026-07-26

TAB now knows the toolchain. Completion for `caustic`, `caustic-as`,
`caustic-ld`, `caustic-mk` and `caustic-lsp`, in **bash** and **zsh**, installed
by `install.sh` and shipped in the release archive.

Every flag comes from the tool's own argument parser rather than from the
README, so the two cannot drift: if `parse_args` accepts it, TAB offers it, and
if it does not, TAB stays quiet.

## What each one completes

**`caustic`** — every flag, every target triple (with a one-line description of
each in zsh), the CSE modes and extensions, and `.cst` sources. `-o` offers the
name the target on the line will actually produce:

```
$ caustic hello.cst -o <TAB>                              hello
$ caustic --target=windows-x86_64 hello.cst -o <TAB>      hello.exe
$ caustic --target=wasm32-wasi hello.cst -o <TAB>         hello.wasm
$ caustic --shared hello.cst -o <TAB>                     libhello.so
$ caustic --target=caustic-x86_64 --shared … -o <TAB>     libhello.csl
```

`-l<name>` lists the libraries actually installed next to the binary, not a
guess.

**`caustic-ld`** — every flag including the CSE ones, `.o`/`.obj` for inputs,
and for `--image=` / `--cst=` a glob that reaches past the extension: a pure
image is `<n>.cse` and a polyglot one `<n>.cse.exe`, so plain `*.cse` would have
hidden half of them. `--pe=` matches `*.exe`, `--elf=` matches anything, because
an ELF has no extension to match on.

**`caustic-mk`** — subcommand-aware:

| after | you get |
|---|---|
| `build` | `all` plus every target in the manifest |
| `run` | every target **and** every script; after the name, files — those arguments belong to the child |
| `info` `why` `graph` `watch` `install` | targets |
| `--profile` | the manifest's profiles |
| `-D` / `--define` | the manifest's `set` keys, then that key's current value once you type the `=` |
| `completions` | `bash`, `zsh` |

The names come from `caustic-mk list` — the binary being completed, so
`./caustic-mk build <TAB>` inside a checkout describes *that* checkout — and
fall back to reading the nearest `Causticfile` directly, so a fresh clone with
nothing built yet still completes.

**`caustic-lsp`** — nothing, deliberately. `lsp/main.cst` is `fn main() as i32`:
no argc, no argv. Without a completion of its own, bash falls back to suggesting
filenames the binary cannot read.

All of them are registered for every name a tool ships under — the plain ELF,
the `.exe`, and the CSE flavours (`caustic-lsp.cse`,
`caustic-universal.cse.exe`, …). Same program, same arguments.

## Fixed

### `--opt=value` completed nothing at all in bash

`=` is one of the characters in bash's default `COMP_WORDBREAKS`. Readline
therefore hands a completion function `--target=lin` as **three** words —
`--target`, `=`, `lin` — and the current word is `lin`, not `--target=lin`.

Every script tested for the value with

```bash
case "$cur" in
    --target=*) ... ;;     # never matches
esac
```

which cannot match, so TAB fell through to the catch-all and listed files. That
was true of `--target=`, `--mode=`, `--entry=`, `--base=`, `--stack-size=`,
`--extension=`, `--image=`, `--pe=`, `--cst=` — in other words, of every option
whose value is worth completing at all.

The shared helper block now reassembles the split and answers **without** the
`--opt=` prefix, because readline only replaces the text after the `=`. It also
handles the other direction, for a shell configured with `=` removed from
`COMP_WORDBREAKS`, where the word does arrive whole.

### `caustic-mk completions <shell>` emitted a snapshot

It composed a script on the spot with the *current* manifest's target and script
names written in as a literal list. That sounds like the one thing a generic
completion script cannot know, and is the opposite of useful: a completion is
installed once and then used in every project, so the copy in
`~/.zsh/completions` described one checkout forever — offering names that exist
nowhere else and hiding the ones that do.

It now prints the shipped script, which reads the project at completion time. It
also no longer needs a `Causticfile` to run, which is exactly where you are when
setting your shell up.

## Installing them

`install.sh` takes `--completions=bash,zsh` and defaults to whichever of the two
shells is present. Files land where each shell already looks —
`<prefix>/share/bash-completion/completions/<command>` and
`<prefix>/share/zsh/site-functions/_<command>` — and are recorded in the install
manifest, so `uninstall.sh` removes exactly those and `update.sh` replays the
choice. A completion in a directory the shell never reads fails silently, so the
installer checks `$fpath` and `XDG_DATA_DIRS` and prints the one line to add
when they do not cover the prefix.

Without installing anything:

```sh
caustic-mk completions bash > ~/.local/share/bash-completion/completions/caustic-mk
caustic-mk completions zsh  > "${fpath[1]}/_caustic-mk"
```

## How they are tested

`tools/completions/selftest.sh` runs the bash functions for real, building
`COMP_WORDS` / `COMP_CWORD` exactly as readline does — including the `=` split,
verified against an interactive bash. A test that handed the function one tidy
word would have declared the bug above fixed while it was still there.

For zsh it drives an actual completion widget on a pty, because `_arguments`
only runs inside one: a real zsh loads the functions the way `compinit` does,
presses TAB, and the listing it paints is what gets asserted. 92 checks, part of
the pre-commit gate.

## Bootstrap

The shipped binaries are the settled 4th generation of an `-O2` self-host, built
in four sequential phases: an `-O2` seed, the compiler to gen4, the toolchain to
gen4 by that compiler, then the compiler to gen4 once more on top of the settled
toolchain. Phase 4 reproduced phase 2 exactly.

| binary | sha256 (first 16) |
|---|---|
| `caustic` (phase-4 gen4) | `290a824cd22dba52` |
| `caustic-as` | `3ed026bd3f58507b` |
| `caustic-ld` | `340c10aabbc89df2` |
| `caustic-mk` | `b5091cdced763b6c` |
| `caustic-lsp` | `b6744d8cd1ba720a` |

Self-host fixpoint verified at `-O0`, `-O1` and `-O2`: gen2 == gen3 == gen4,
byte-identical, gen4 output correct; 21 examples identical across the three
levels; test suite 18/18; cross-target builds clean for linux/windows/caustic ×
x86_64/aarch64 plus `libcaustic.so` / `.dll` / `.csl`; `caustic-mk`'s own suites
151 unit + 136 integration.
