# v0.1.7 — 2026-08-01

Threads work at `-O1`.

They did not, for as long as `std/thread.cst` has existed, on every program
that spawned one. The failure was a segfault with no diagnostic, and the
diagnosis that circulated — "the assembler resolves a local label to the wrong
address" — described the last link in the chain rather than the first. What
follows is the whole chain, because the shape of it is more useful than the
patch.

## The bug

`pass_inline` decides what a callee may be, and one of its gates is:

```
found.alloc_stack_size == 0
```

The intent is "no stack frame whose offsets would clash with the caller's".
The effect is the opposite of what it reads like. An ordinary function with a
parameter materializes a stack slot for it, so `alloc_stack_size` is non-zero
and the gate rejects it. A `with naked` function has no prologue at all, so
`alloc_stack_size` is zero **no matter how many arguments it takes**.

The pass written to inline small leaf helpers had, in practice, made asm
trampolines its most eligible candidates. `_clone_thread` is five arguments,
one `asm`, no frame, two live IR instructions — under every limit the pass has,
and inlined into `spawn` at `-O1`.

Duplicating an inline asm body breaks it two independent ways, and either half
alone is fatal:

**The label.** A label written inside the asm text is emitted wherever the body
is. Inlined at two call sites, it is defined twice in the `.s`. The assembler's
symbol table is keyed by name with no per-function scope, and `sym_find_or_add`
only updates a symbol while it is still a forward reference — so the first
definition kept its offset and every jump to that name resolved there. In the
reported case the `je` ended up pointing into `_start`.

**The `ret`.** The asm text is written against the callee's entry conditions:
arguments in `rdi`/`rsi`/…, and a `ret` that returns from the *callee*. Inlined,
that `ret` returns from the caller, in the middle of an expression, and the
argument registers hold whatever the caller had. Eleven lines reproduce it:

```cst
fn pick(x as i64) as i64 with naked {
    asm("test rdi, rdi\njz .Lzero_case\nmov rax, 111\nret\n.Lzero_case:\nmov rax, 222\nret\n");
}
fn main() as i32 { io.printf("%ld %ld\n", pick(1), pick(0)); return 0; }
```

`111 222` at the default level. At `-O1`, `main` begins with `test %rdi,%rdi`
against its own `argc`, jumps into `_start`, and returns 111 from `main`.

## The fix

`pass_inline` now requires `is_naked == 0` **and** `has_asm == 0`. Both, not
either: a naked body with no label still carries the wrong `ret`, and an
ordinary function with a labelled asm still duplicates the label — and that
second shape is reachable, because a zero-argument function materializes no
stack slot and clears the same gate. Both are in `tests/inline_asm_test.cst`.

`has_asm` is cached beside `has_stack_ops` in both places that compute inline
metadata, since deferred mode fills it in the parent and the workers refill it
after inlining.

Inlining itself is untouched. A function without asm is still inlined and its
symbol still disappears.

## Two things found on the way down

**`bins_new` and `bins_custom` never wrote the lock word.** Both build their
result in a local `Bins`, which arrives holding whatever the previous frame
left at that offset. Every other field is written on some path; that one was
written on none. Nothing notices while the program is single-threaded, because
`core._lk` is a no-op until `mem.set_mt()` — and after that, the first
allocation through such a heap finds a non-zero lock, futex-waits on a lock
nobody holds, and never wakes. The process stops with no error and no crash.

`tests/threads/t_alloc_mt.cst` does exactly this construction and has been
passing all along, which is the problem: it passes when that stack slot happens
to hold a zero. The new `tests/bins_lock_test.cst` dirties the stack with a
non-zero pattern before each construction and then reads the word, so it fails
every time instead of most times. Its deterministic checks run before the
threaded exercise on purpose — on a broken build the process exits at check 1
and never reaches the allocation that would hang, and a test that hangs does
not report a failure, it holds the suite open until someone kills it.

**Five mmap constants were declared twice in `std/os/linux.cst`.**
`PROT_NONE`, `PROT_READ`, `PROT_WRITE`, `MAP_PRIVATE` and `MAP_ANONYMOUS`, once
near the top with the other mmap flags and again 450 lines down under "mmap
PROT/MAP for thread stacks". The values matched, so nothing ever misbehaved.
Found the moment the assembler started refusing duplicate definitions, which is
the argument for refusing them: it sat there because nothing could tell anyone.

## The assembler says so now

A label defined a second time is an error naming the symbol and the line,
instead of the first definition silently winning. `.globl foo` before `foo:` is
a forward reference and is not caught — only a name that already carries a real
section.

The compiler side is fixed, so this catches nothing today. It exists because
the next producer of a bad `.s` should hear about it where it lands rather than
at runtime.

A duplicate module-level `let` still surfaces here as a mangled symbol name
rather than a source-level diagnostic. Catching it in the semantic layer is the
better error and a separate change.

*(Addendum: that landed in v0.1.9, which names the file, the line and the name.
Everything above describes v0.1.7 as it shipped.)*

## The suite runs both backends

Everything in `tests/run_tests.cst` ran at the default level, and the bootstrap
fixpoint was the only thing in the file that ever passed `-O1`. That is how an
`-O1`-only pass broke every threaded program without a single test noticing.

The seven thread tests and the new asm test now run at both levels. 25 checks
to 36.

Verified against the previous compiler: all four spawn-based thread tests exit
139 at `-O1` there and pass here, at both levels.
