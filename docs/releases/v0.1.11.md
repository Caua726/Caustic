# v0.1.11 — 2026-10-02

Two float miscompiles at `-O1` and `-O2`, a terminal reader that reads events
instead of bytes, display widths in columns, and builds from source that say
which commit they are.

## If you installed with the one-liner, you have v0.1.6

This is the first release published on GitHub since v0.1.6. v0.1.7 through
v0.1.10 were tagged and never released, and `install.sh` downloads the latest
*release*, not the latest tag — so a plain install kept handing out v0.1.6 the
whole time, and `update.sh` agreed it was current. Everything in those four
versions reaches you for the first time here; they are summarised at the end.

`tools/prerelease.sh` compared the new version against the newest tag, which is
why nothing noticed. It now names every tag past the release the installer
actually serves.

## Floats at `-O1` and `-O2`

**A float compared against `0.0` was compared against a stale register.**
`pass_fold_immediates` turns a compare's constant operand into an immediate when
its bits fit in 32, and the bits of `0.0` are zero, so every `x > 0.0`,
`x < 0.0`, `x <= 0.0` and `x >= 0.0` was folded. The integer compare checks for
the immediate. The float compare loaded the operand by vreg number, which after
folding names whatever that register last held. A loop whose condition read
such a compare stopped early, and a graphics suite drew nothing while reporting
frames twenty times faster than the real ones. At `-O0` nothing folds, and the
compiler self-hosts without comparing a float against zero, so neither the
bootstrap nor the suite saw it.

**An if-converted select of floats read `rax`.** `if (c) { x = y; }` becomes
`IR_CMOV`, and from `-O1` a float `x` or `y` may live in an XMM register.
`gen_inst_cmov` named any register location with `reg64()`, which answers `rax`
for every XMM location — and `rax` had just been overwritten by the `setcc` of
the float compare producing the condition. A running minimum,
`if (b < hi) { hi = b; }`, came out as 5e-324.

Both have tests that run at every level and failed at `-O1` and `-O2` before.

## The terminal reads events

`std/term.cst`'s `read_key()` decided what it had from the third byte of an
escape sequence and handed the rest back as keystrokes. An SGR mouse report
arrived as Escape plus eight keys; an OSC reply a terminal sends unasked, as
twenty-three, the first of them whatever opens a menu.

Reading and parsing are separate now. A pure scanner either produces one event
or asks for more bytes; a buffered reader owns the descriptor. The new surface
is `Event`, `Input`, `input_open` / `input_close` / `input_fd` / `input_next`:
keys, SGR-1006 mouse, bracketed paste as one `EV_PASTE`, and focus.
`input_close` puts back exactly the modes `input_open` turned on. `read_key()`
keeps its signature as a shell over the module's own reader, `shared_input()`.

Fixed on the way, each measured on a real pty before and after:

- a sequence of any introducer — CSI, SS3, OSC, DCS, APC, PM, SOS, SS2 — is
  consumed whole or not at all, and one longer than the buffer is skipped to
  its terminator instead of typed;
- a bracketed paste through `read_key` comes out as the keys it would have been
  instead of being dropped;
- `ESC ESC x` no longer loses the `x`;
- a twenty-digit coordinate is refused instead of wrapping into a valid one, and
  a report for a cell the terminal does not have is dropped;
- an over-long or out-of-range modifier is refused instead of becoming
  Shift+Alt+Ctrl;
- a burst of focus reports no longer hangs the reader with the typing behind it
  thrown away;
- a pause inside a paste or a sequence no longer ends it, within a bounded hold;
- the NUL byte (Ctrl+Space) answers `KEY_NUL` (1009) instead of the `0` that
  means "nothing happened".

The Windows path compiles and has never been run, which the module header says.

## Columns, not bytes

`std/unicode.cst` answers how many terminal columns text takes, grapheme-cluster
aware: a ZWJ family is one cluster of two columns, a flag is two, a heart with
a variation selector is two. `cluster_next` walks one cluster from a boundary
and allocates nothing, for a renderer measuring every visible line;
`string_width`, `cp_width` and UTF-8 decode sit beside it. Its two megabytes of
generated tables are why it is not in `libcaustic.cst`.

## A build from source says which commit it is

`src/version.cst` only moves when a release is cut, so an install from the
latest commit answered `caustic 0.1.10` twenty-two commits later, and two such
builds could not be told apart. `install.sh --from-source` now derives the
version from `git describe`:

```
on the tag v0.1.11            0.1.11
5 commits past it             0.1.12-dev.5+1a2b3c4
with uncommitted edits        0.1.12-dev.5+1a2b3c4.dirty
```

A commit past a release is a pre-release of the next patch, so SemVer orders
them after the release they follow and before the next one. The version is
written into the tree for the build and the file put back afterwards — your own
checkout is left as it was. The compiler is untouched: a source build is
compiled by the latest release, which would not know a new flag.

The install manifest records `build=source`, the branch and the commit.
`update.sh` checks a source install against its branch on GitHub and rebuilds
it from source, instead of comparing it with the latest release and offering to
replace it. An install built from source before this release, which the
manifest cannot say, is newer than the release it would be "updated" to;
`update.sh` now says so and leaves it alone.

A system install also asks for the password once instead of once per file:
pkexec keeps no authorization between calls, so the steps are queued and run
under one escalation.

## Also new since v0.1.6

From the four tagged versions that were never released. Full entries are in
[`CHANGELOG.md`](https://github.com/Caua726/Caustic/blob/main/CHANGELOG.md).

- **v0.1.7 — threads work at `-O1`.** The inliner took `with naked` clone
  trampolines for ideal leaf helpers and inlined `_clone_thread` into `spawn`,
  so every threaded program segfaulted at `-O1`. A heap built by `bins_new` or
  `bins_custom` carried stack garbage in its lock word and hung the first
  multithreaded allocation. The assembler now refuses a label defined twice
  instead of keeping the first, which found five duplicate constants in
  `std/os/linux.cst`. [Full notes](https://github.com/Caua726/Caustic/blob/main/docs/releases/v0.1.7.md).
- **v0.1.8 — `[MAX]u8` in a struct works in an imported module**, not only in
  the root file. Each module's constants are now in scope for its own layout,
  and two modules may use the same constant name with different values.
- **v0.1.9 — a second top-level `let` of the same name is an error** with file,
  line and name. It used to bind the second initializer to the first variable.
  Shadowing a local in an inner scope is still legal.
- **v0.1.10 — two silent ceilings on constant data.** A string literal of
  32768 characters was truncated by an `i16` in the assembler, and `bins_alloc`
  refused anything over 64 KiB, which the compiler's own `str_dup` then carried
  as a null. A 2 MB literal round-trips.

The test suite also runs `-O2` now, not only the default level and `-O1`.

## Upgrading

Two changes can reject code that compiled on v0.1.6:

- a duplicate top-level `let` is an error (v0.1.9). The code was already broken
  — both declarations shared one variable — but it used to build;
- `std/term.cst`'s old module-level `Input` pointer is gone, so naming it is a
  compile error. Pass `shared_input()` to `input_open` to share one reader
  between `read_key` and `input_next`.

`read_key()` answers differently where it used to be wrong: unrecognised
sequences, mouse and focus reports produce `KEY_NONE` instead of keystrokes, and
Ctrl+Space produces `KEY_NUL` instead of `0`.
