# v0.1.4 — 2026-07-26

A correctness release. The headline is a compiler segfault that only appeared
under `--cache`, and the two bugs that let it go unnoticed for a while.

## Fixed

### A function type's parameters were read as if they were struct fields

`Type.fields` carries two different things depending on the kind:

| kind | `fields` holds |
|---|---|
| struct / enum | a linked list of `*Node` |
| `TY_FN` | a **packed array of `*Type`** — the parameter types |

The AST cache read it as a node list unconditionally, in all three places that
touch it (`collect_type`, `serialize_type`, `fixup_type_fields`). Walking a
function type's parameter array as a node list reinterprets a `*Type` as a
`*Node`, reads whatever happens to sit where `ty` or `return_type` would be, and
recurses into it.

Nine lines reproduce it:

```caustic
struct S {
    op   as fn(*u8) as i64;
    next as *S;
}
fn main(argc as i64, argv as i64) as i32 { return cast(i32, 0); }
```

```
$ caustic -c s.cst --cache .caustic
Segmentation fault
```

Only under `--cache` — nothing else in the pipeline walks that field
generically, so it stayed hidden until a build system started passing `--cache`
by default. It then showed up on exactly one file out of ninety-nine: the first
one whose types happened to reach a struct with a function-pointer member. A
vtable-shaped struct, which is a shape systems code uses constantly.

`collect_type` now branches on the kind. `serialize_type` writes a `TY_FN`'s
parameter types into the **GA side-table** — the same mechanism generic
arguments already use — and stores the start index in the record slot that holds
a node index for other kinds. The kind sits at offset 0 of that same record, so
the reader can never guess wrong. `fixup_type_fields` rebuilds the packed array
from the table.

**Cache format 5 → 6.** A v5 image read as v6 would resolve parameter types
against the node table, so the bump is mandatory. Stale caches are invalidated
automatically; there is nothing to clean by hand.

### A child killed by a signal was reported as having exited successfully

`std/process.wait_pid` decoded the wait status with a bare `(status >> 8) & 255`.
That is `WEXITSTATUS`, and it means something **only when the child exited**. A
child killed by a signal leaves the signal number in the low seven bits and
**zero** in the high byte — so every crash decoded to `0`, which is success.

This is what kept the bug above quiet: the compiler segfaulted, the build system
was told it had succeeded, and a target went missing without one line of output
saying so.

New `std/process.exit_code_of` decodes properly and reports a signal death as
`128 + signal`, the shell convention — `139` for `SIGSEGV`, distinguishable from
any exit code a program can return.

## Verification

- The compiler rebuilds itself under the new cache format to a **byte-identical**
  binary.
- Self-host fixpoint at `-O0`, `-O1` and `-O2`: gen2 == gen3 == gen4, all
  byte-identical, gen4 output correct.
- 21 examples identical across `-O0`/`-O1`/`-O2`; test suite 18/18.
- Cross-target builds clean for linux/windows/caustic × x86_64/aarch64, plus
  `libcaustic.so` / `.dll` / `.csl`.

## Also in this release

- **`SYS_CHAN_INFO`** — how much a channel will take right now, so a writer can
  ask instead of discovering it by failing.
- **Installers**: arrow-key menus on both systems, an existing install is
  noticed, building from source folds into the same flow, and the PowerShell
  scripts run on Linux and on 5.1. Prompting is a decision now, not something
  that happens because stdin is a terminal.
- **`--mode=pure` output is named `.cse`**, not `.cse.exe`.
